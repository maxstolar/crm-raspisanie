# Переезд расписания на GitLab и стенд

Документ для сессии, в которой будем переносить расписание. Прикрепите его к запросу
целиком: он описывает, как система устроена сейчас, как она должна выглядеть на стенде
и в каком порядке переезжать, чтобы старые ссылки не ломались ни на минуту.

Документ не привязан к конкретному стенду. Всё, что зависит от стенда, вынесено
в раздел «Что выяснить в начале сессии».

Составлено 23 сентября 2026 по состоянию `main` в `maxstolar/crm-raspisanie`.

## 1. Зачем переезд

Сейчас всё держится на личном аккаунте GitHub владельца:

- **Хранилище.** Данные, фото и история версий лежат в публичном репозитории
  `maxstolar/crm-raspisanie`.
- **Публикация.** Страница пишет в этот репозиторий прямо из браузера через GitHub API.
  Токен с правом записи лежит в исходнике страницы, разбитый на три части.
- **Выкладка.** Подрядчик по таймеру забирает содержимое `assets/` из этого репозитория
  на `https://mindbox.ru/storage/raspisanie-shkoly-crm/`. Фактическая задержка —
  3–4 часа.

Цель: репозиторий живёт в корпоративном GitLab, стенд сам отдаёт страницу и данные,
токена на странице нет, таймера нет, правки видны за секунды.

## 2. Как устроено сейчас

### Файлы

```
assets/
├── index.html        страница и редактор целиком, ~350 КБ, без сборки
├── guide.html        публичная справка для редакторов
├── data.json         расписание основного адреса
├── data-2.json       расписание второго адреса («Третий поток • Зима 2027»)
├── data-test.json    черновик
├── speakers.json     список спикеров; появится при первой правке спикеров
└── avatars/          фото спикеров, PNG 120×120, плюс workshop.png и README.txt
README.md             подробное описание всех решений; на витрину не идёт
```

На витрину идёт **содержимое** `assets/`: оно раскладывается в корень адреса.
`assets/avatars/x.png` открывается как `…/raspisanie-shkoly-crm/avatars/x.png`.

### Адреса

Схему адресов на стенде нужно сохранить **без изменений**: тогда перенаправление со
старого адреса — это простая замена начала ссылки.

| Адрес | Файл | Кому |
|---|---|---|
| `…/` | `data.json` | студентам текущего потока |
| `…/?stream=2` | `data-2.json` | студентам следующего потока |
| `…/?stream=N` | `data-N.json` | появляется сам при первой публикации |
| `…/?test` | `data-test.json` | черновик, только редакторам |
| любой из них с `#edit` | тот же | вход в редактор |
| `…/guide.html` | — | справка для редакторов, открыта всем |

Номер в адресе — это адрес, а не номер потока. Название потока хранится в поле
`title` файла расписания и показывается подписью под заголовком.

### Форматы данных

Файл расписания:

```json
{
  "title": "Третий поток • Зима 2027",
  "months": [
    {"name": "Сентябрь", "ndays": 30, "c1": 1, "labelY": 546, "wdY": 708.4, "row0": 781.8, "nrows": 5}
  ],
  "data": {
    "Сентябрь": {
      "1": {"type": "g", "t": "17:00 — 19:00", "ttl": "CRM‑маркетинг в бизнесе",
            "sp": [["Петр Ермаков", "ermakov"]]}
    }
  }
}
```

- `type`: `g` вебинар, `s` текст, `y` важная дата, `k` чёрная пятница.
- `ttl`: строка или массив строк. `sp`: до двух пар `[имя, файл фото без .png]`.
- Необязательные поля занятия: `bt` бейдж, `nb` без бейджа, `sm` мелкий шрифт,
  `deco` и `viz` спец-визуал.
- Поля месяца `labelY`, `wdY`, `row0`, `nrows` страница пересчитывает сама.

`speakers.json`:

```json
{"speakers": [{"name": "Петр Ермаков", "file": "ermakov"}]}
```

Страница дополняет список спикерами из занятий этого расписания и основного адреса,
поэтому отсутствие файла — нормальное состояние.

### Все обращения страницы к GitHub

Это полный список того, что нужно заменить.

| Что делает страница | Функция в `index.html` | Запрос сейчас |
|---|---|---|
| Читает расписание | `loadSchedule`, `fetchStreamSchedule` | `raw.githubusercontent.com/…/assets/data*.json`, запасной путь — относительный `data*.json` |
| Читает список спикеров | `loadSpeakers` | raw `speakers.json`, запасной — относительный |
| Показывает фото | `avaHTML`, `imgFallback` | относительный `avatars/x.png`, при промахе — raw GitHub |
| Публикует расписание | `publish` → `ghPutFile` | `PUT /repos/…/contents/assets/data*.json` |
| Заливает черновик в расписание | `promoteToStream` → `ghPutFile` | то же, в выбранный файл; файл создаётся, если его нет |
| Список расписаний для переноса | `listSchedules` | `GET /repos/…/contents/assets` + raw каждого файла ради `title` |
| История публикаций | `openHistory` | `GET /repos/…/commits?path=…&per_page=20` |
| Загрузить версию из истории | `loadVersion` | `GET /repos/…/contents/<file>?ref=<sha>` |
| Защита от перезаписи чужой правки | `ghPutFile(…, expectedSha)` | сверка `sha` текущего файла перед записью |
| Загрузить или заменить фото | `uploadAvatarFile` → `ghPutFile` | `PUT …/contents/assets/avatars/<slug>.png` |
| Удалить фото | `ghDeleteFile` | `DELETE …/contents/assets/avatars/<slug>.png` |
| Фото без имени | `listOrphanAvatars` | `GET …/contents/assets/avatars` |
| Сохранить список спикеров | `saveSpeakers` → `ghPutFile` | `PUT …/contents/assets/speakers.json` |

Константы, которые уйдут: `GH_OWNER`, `GH_REPO`, `GH_BRANCH`, `RAW_BASE`,
`GH_TOKEN_PARTS`, `GH_TOKEN`. Константа `EDIT_PASS` тоже уходит со страницы: пароль
начинает проверять сервер.

### Соглашения, от которых зависит поведение

- **Сообщения коммитов** пишутся по-русски, время московское:
  `schedule: обновление 2026-09-21 16:40 МСК`,
  `schedule: залито из черновика в data-2.json 2026-09-21 16:40 МСК`,
  `avatar: <slug> (<время> МСК)`, `avatar: удалён <slug> (<время> МСК)`,
  `speakers: <что сделано> (<время> МСК)`.
  «История» помечает заливки из черновика по фразе `залито из черновика`
  или старой `залито из теста`. Формат надо сохранить.
- **Таймауты.** Чтение данных — 5 секунд, запись — 20 секунд. Без них недоступная сеть
  вешает страницу до TCP-таймаута.
- **Три исхода загрузки** различаются в интерфейсе: данные есть; источник ответил, что
  файла нет, это нормально для нового адреса; источник не ответил — сбой. Серверная
  часть должна отдавать 404 на отсутствующий файл, а не 200 с пустым телом и не 500.
- **Черновик в браузере** хранится в `localStorage` под ключами `mbx_schedule`,
  `mbx_schedule_N`, `mbx_schedule_test`. Если домен меняется, несохранённые черновики
  на старом домене останутся там. Перед переключением редакторам нужно опубликовать
  или выбросить свои правки.

## 3. Как должно выглядеть на стенде

### Схема

```
                  ┌──────────────────── стенд ────────────────────┐
браузер ──GET───▶ │ index.html, guide.html        из репозитория  │
        ──GET───▶ │ data*.json, speakers.json, avatars/*          │ ──▶ GitLab: main, assets/
        ──API───▶ │ серверная часть: пароль, запись, история      │ ──▶ GitLab API
                  └───────────────────────────────────────────────┘
```

Три правила:

1. **GitLab — единственный источник правды.** Всё, что меняет редактор, — коммит в `main`.
   История версий и откаты работают поверх истории git, как сейчас.
2. **Токен GitLab живёт только на сервере.** Для записи через API GitLab нужен токен
   с правом `api`. Такой токен умеет гораздо больше, чем писать файлы: запускать
   пайплайны, читать задачи. На публичной странице ему не место, даже разбитому на части.
3. **Никакого таймера.** Стенд узнаёт об изменениях сам: по вебхуку или через CI на
   каждый коммит в `main`.

### Контракт стенда: что по какому адресу отдаётся

Базовый адрес дальше — `<BASE>`, например `https://<стенд>/raspisanie-shkoly-crm/`.

| Путь | Что | Свежесть | Кэш |
|---|---|---|---|
| `<BASE>` и `<BASE>index.html` | `assets/index.html` из `main` | до минуты после коммита | `no-cache` |
| `<BASE>guide.html` | `assets/guide.html` | до минуты | `no-cache` |
| `<BASE>data.json`, `data-N.json`, `data-test.json` | файлы из `assets/` | **до 10 секунд** после коммита | `no-cache` |
| `<BASE>speakers.json` | `assets/speakers.json`, 404 если нет | до 10 секунд | `no-cache` |
| `<BASE>avatars/<slug>.png` | фото, 404 если нет | до минуты | `max-age=300`; после замены страница добавляет `?v=` |
| `<BASE>api/…` | серверная часть, см. ниже | — | `no-store` |

Content-Type: `.html` — `text/html; charset=utf-8`, `.json` — `application/json; charset=utf-8`,
`.png` — `image/png`. Файлы отдаются как есть, без минификации и переписывания ссылок.

Все пути **относительные к `<BASE>`**, поэтому страница не знает свой домен и чтение
данных в ней почти не меняется: пропадает только первый источник с GitHub.

Как добиться свежести, решаем по стенду. Два нормальных варианта:

- **Локальная копия репозитория на стенде**, веб-сервер отдаёт `assets/` из неё. Вебхук
  GitLab на push в `main` делает `git pull`. Самый простой и быстрый, нужен ключ
  развёртывания только на чтение.
- **Прокси к GitLab** для данных и фото с кэшем на 5–10 секунд и отдачей последней
  удачной копии, если GitLab недоступен. Код страницы при этом выкладывает CI.

Не годится: CI-пайплайн на каждую публикацию данных. Редакторы жмут «Опубликовать»
по многу раз подряд, в истории есть девять публикаций подряд, две из них в одну минуту,
и очередь пайплайнов даст задержку в минуты.

### Серверная часть: контракт API

Если стенд на Laravel, это один контроллер и middleware для пароля. Язык не важен,
важен контракт.

**Настройки сервера**, в переменных окружения, не в коде:

| Переменная | Что |
|---|---|
| `GITLAB_URL` | адрес GitLab |
| `GITLAB_PROJECT_ID` | ID проекта или `группа%2Fпроект` |
| `GITLAB_BRANCH` | `main`; на время проверки — тестовая ветка |
| `GITLAB_TOKEN` | project access token, роль Developer или Maintainer, право `api` |
| `EDITOR_PASSWORD` | пароль редактора |
| `ALLOWED_ORIGINS` | откуда можно ходить к API; обычно только сам стенд |

**Имена файлов сервер собирает сам** из проверенных параметров. Никогда не принимайте
путь из запроса.

- слот: `main` → `data.json`, `test` → `data-test.json`, целое `2…99` → `data-N.json`;
- фото: slug по `^[A-Za-z0-9_-]{1,64}$` → `assets/avatars/<slug>.png`.

**Эндпоинты:**

| Метод и путь | Доступ | Что делает | Вызов GitLab API |
|---|---|---|---|
| `POST api/login` `{password}` | все, с ограничением частоты | проверяет пароль, отдаёт `{token}` на 12 часов | — |
| `GET api/schedules` | редактор | `[{slot, file, title}]` всех расписаний, кроме черновика | `GET /repository/tree?path=assets` + чтение `title` |
| `PUT api/schedule/<slot>` `{data, message, base?}` | редактор | записывает расписание; создаёт файл, если его нет | `PUT` или `POST /repository/files/<path>` с `last_commit_id=base` |
| `GET api/schedule/<slot>/history` | редактор | 20 последних коммитов файла: `id`, `title`, `author`, `date` | `GET /repository/commits?path=…&ref_name=…&per_page=20` |
| `GET api/schedule/<slot>/version/<commit>` | редактор | содержимое файла на этом коммите | `GET /repository/files/<path>/raw?ref=<commit>` |
| `GET api/schedule/<slot>/head` | редактор | `last_commit_id` текущего файла | `GET /repository/files/<path>?ref=…` |
| `PUT api/speakers` `{speakers, message}` | редактор | записывает `speakers.json` | `PUT`/`POST /repository/files/assets%2Fspeakers.json` |
| `GET api/avatars` | редактор | список slug всех фото | `GET /repository/tree?path=assets/avatars` |
| `PUT api/avatars/<slug>` `{png}` base64 | редактор | загружает или заменяет фото | `PUT`/`POST /repository/files/…` с `encoding=base64` |
| `DELETE api/avatars/<slug>` `{message}` | редактор | удаляет фото; 404 не ошибка | `DELETE /repository/files/…` |

Ответы: `200/201` с JSON; `401` неверный или истёкший токен редактора; `404` нет файла;
`409` файл изменился с момента `base` — это «пока вы выбирали версию, расписание
опубликовал кто-то ещё»; `502` GitLab не ответил. Текст ошибки — по-русски, страница
показывает его как есть.

**Защита от перезаписи.** На GitHub страница сверяла `sha` файла. В GitLab тот же смысл
у `last_commit_id`: если передать его в `PUT` или `DELETE`, GitLab откажет, когда файл
успели изменить. Сейчас сверка есть только при откате из «Истории». На стенде её стоит
включить для каждой публикации: страница помнит `head` с момента загрузки и отправляет
его как `base`. Это закрывает старую проблему «побеждает тот, кто опубликовал последним».

**Сообщение коммита** формирует страница, как сейчас. Сервер проверяет, что оно
начинается с `schedule:`, `avatar:` или `speakers:` и короче 200 символов.

**Автор коммита** будет одним ботом проекта. Если нужно видеть, кто из редакторов
публиковал, можно спрашивать имя при входе и дописывать его в сообщение. Это не
обязательно для переезда.

- **`README.md`.** Разделы «Как это устроено», «Токен GitHub», «Витрина и домен»

## 4. Порядок переезда

Старые ссылки работают на каждом шаге. Правило одно: **в каждый момент расписание пишется
ровно в одно место.** Редакторы публикуют почти каждый день.

### Шаг 1. Подготовка — старое не трогаем

1. Создать проект в GitLab и перенести репозиторий **с полной историей**: на ней держится
   «История» и откаты.

   ```bash
   git clone https://github.com/maxstolar/crm-raspisanie.git
   cd crm-raspisanie
   git remote add gitlab <адрес проекта в GitLab>
   git push gitlab --all
   git push gitlab --tags
   ```

   Не используйте `git clone --mirror`: он тащит служебные `refs/pull/*` GitHub,
   и GitLab отказывается их принимать.

2. В истории лежит токен GitHub: один раз открытым текстом в `fe763c0`, дальше
   разбитым. Первый уже отозван. Сканер секретов GitLab может на него ругаться — это
   ожидаемо; после отзыва второго токена на шаге 2 оба безвредны.
3. Собрать стенд по разделу 3. Серверную часть направить на **тестовую ветку**
   `stand-test`, не на `main`: пока `main` в GitLab — копия, в неё не должно попадать
   ничего, кроме синхронизации с GitHub.
4. Правки страницы делать в ветке и MR в GitLab. До переключения не вливать.
5. Проверить на стенде всё по чек-листу из раздела 5.

Пока идёт подготовка, редакторы работают как раньше на `mindbox.ru`, и изменения
продолжают попадать в GitHub.

### Шаг 2. Переключение — полчаса тишины

Выбрать время, когда никто не публикует, и предупредить редакторов заранее: опубликовать
или выбросить несохранённые правки и полчаса ничего не нажимать.

1. **Отозвать токен GitHub** в настройках fine-grained токенов. Старый редактор
   на `mindbox.ru` сразу перестаёт публиковать и честно пишет, что токен недействителен.
   Смотреть старые ссылки по-прежнему можно.
2. **Последняя синхронизация** GitHub → GitLab:

   ```bash
   git pull origin main
   git push gitlab main
   ```

3. **Влить MR** с правками страницы в `main` GitLab, переключить серверную часть
   на `main`, убедиться, что стенд отдаёт новую страницу.
4. **Пройти чек-лист** из раздела 5 на стенде. Если что-то не так, откат простой:
   выпустить новый токен GitHub, вернуть его в старую страницу. Данные не потеряны,
   GitHub ничего не пропустил.
5. **Сделать старый адрес переходником.** Последний коммит в GitHub: `assets/index.html`
   заменяется на короткую страницу, которая переносит на стенд, сохраняя хвост адреса:

   ```html
   <!doctype html>
   <meta charset="utf-8">
   <title>Расписание переехало</title>
   <script>location.replace('<BASE>' + location.search + location.hash);</script>
   <p>Расписание переехало: <a href="<BASE>">&lt;BASE&gt;</a></p>
   ```

   `location.search` сохраняет `?stream=2` и `?test`, `location.hash` — `#edit`.
   Без этого студенты второго потока молча попадут на расписание первого.
   Так же заменить `assets/guide.html` переходником на `<BASE>guide.html`.

   Подрядчик увезёт переходник своим таймером, через 3–4 часа. До этого старый адрес
   показывает последнее расписание из GitHub, а публикация там не работает — редакторы
   уже работают на стенде.

6. Когда витрина отдаёт переходник, проверить `…/`, `…/?stream=2`, `…/?test#edit`,
   `…/guide.html`: каждый должен привести на соответствующий адрес стенда.

### Шаг 3. Уборка

## 6. Известные проблемы, которые переезжают вместе с кодом

Не блокируют переезд. Их удобно чинить заодно, пока меняется слой записи.

1. **Нельзя залить черновик в новый адрес.** Список «Залить в расписание…» строится из
   существующих файлов, поэтому следующий свободный адрес в нём не появляется. Сейчас
   заняты `data.json` и `data-2.json`, и залить черновик на `?stream=3` нельзя. Нужно
   всегда добавлять в список строку «следующий адрес · пока пусто».
2. **Выбор расписания — браузерный `prompt`** с вводом номера строки. Лучше окно
   со списком, как у «Истории».
3. **Сверка перед публикацией** есть только при откате из «Истории»; см. раздел 3.
4. **Тесты не хранятся в репозитории** по решению владельца. Сценарии проверки
   описаны в чек-листе выше.

## 7. Что выяснить в начале сессии

Ответы определяют реализацию раздела 3. Остальное в документе от них не зависит.

1. Адрес стенда и базовый путь `<BASE>`.
2. На чём стенд: Laravel, отдельный контейнер, Kubernetes, просто nginx. Где будет жить
   серверная часть.
3. Как стенд узнаёт о коммитах: вебхук и `git pull` или прокси к GitLab.
4. Адрес проекта в GitLab и кто создаёт project access token для сервера.
5. Будет ли у сессии доступ к GitLab: токен в переменной окружения `GITLAB_TOKEN`
   в настройках облачного окружения. Без него сессия подготовит код и инструкции,
   а выкатит тот, у кого есть доступ.
6. Кто со стороны подрядчика поставит перенаправление на шаге 3.

Задачи и MR по стенду велись в сессии Claude Code `mindbox-ops` 11–12 сентября,
проект `mindbox-laravel/mindbox-ops` на `git.intensa-dev.ru`, ветка `cdp-belt-depth`.
