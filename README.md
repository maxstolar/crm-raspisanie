# Расписание школы CRM-маркетологов Mindbox

Одна вертикальная веб-страница со скрытым редактором. Ни сборки, ни бэкенда:
редактор публикует правки прямо в этот репозиторий через GitHub API.

**Редактор:** любой из адресов ниже с `#edit`, пароль в `EDIT_PASS` (см. ниже)

## Потоки

Потоки школы идут параллельно: пока один учится, следующему уже нужно раздать
расписание. Поэтому каждое расписание живёт на своём адресе и в своём файле, ничего
не переключается и ничего не заменяется.

| Адрес | Файл | Что это |
|---|---|---|
| https://mindbox.ru/storage/raspisanie-shkoly-crm/ | `data.json` | основной адрес |
| тот же адрес с `?stream=2` | `data-2.json` | второй адрес |
| тот же адрес с `?test` | `data-test.json` | черновик |

**Номер в адресе — это адрес, а не номер потока.** Первый поток школы прошёл ещё до
появления этого инструмента, без расписания, поэтому счёт адресов и счёт потоков
разошлись и совпадать не обязаны. Страница нигде не выводит номер из адреса как номер
потока: какой это поток, знает только человек, вписавший название.

Следующий адрес появится без правок кода: `?stream=3` читает и пишет `data-3.json`.

**Название задаёт редактор, и оно хранится в файле расписания** (поле `title`).
Имена сезонные, без номеров: «Осенний поток 2026», «Зимний поток 2027». Тогда вопрос
нумерации не возникает вовсе и разъехаться ей негде.

Под заголовком страницы показывается подпись — серый ярлык с этим названием. Сама
подпись не кнопка, нажать её нельзя; в режиме редактирования рядом появляется
маленькая плашка «переименовать», в той же манере, что «удалить месяц» рядом
с месяцем. У черновика подпись жёлтая.

Если названия нет, **подписи нет вовсе** — страница не придумывает номер. В режиме
редактирования вместо неё виден адрес: «без названия · ?stream=2». Это факт о том,
где лежит файл, спутать его с номером потока нельзя, и студенты этого не видят.

Переименование не двигает данные: какой файл читается и пишется, решает адрес.
Иначе смена названия означала бы переезд расписания, и редактор случайно потерял бы его.

Изоляция по файлам заодно снимает вопрос про совпадающие месяцы: года в модели
данных нет, месяц опознаётся по названию, и два сентября в одном файле не поместились
бы. У разных потоков это разные файлы, так что пересекаться они могут как угодно.

## Структура

```
assets/
├── index.html         ← страница и редактор целиком (шрифт, лого, вёрстка вшиты)
├── data.json          ← расписание основного адреса
├── data-2.json        ← расписание второго адреса, появляется после первой публикации
├── data-test.json     ← черновик, появляется после первого сохранения
└── avatars/           ← фото спикеров и workshop.png
```

На витрину идёт **содержимое** `assets/` — оно раскладывается в корень адреса.
То есть `assets/data.json` открывается как `/storage/raspisanie-shkoly-crm/data.json`,
а `assets/avatars/x.png` — как `/avatars/x.png`. Вложенного `/assets/` на витрине нет.
README и прочее в корне репозитория на витрину не попадают.

## Как это устроено

Расписание хранится не в вёрстке, а в JSON. Страница ищет его по цепочке
и останавливается на первом источнике с годными данными:

1. свой файл напрямую с `raw.githubusercontent.com` — свежие данные, кэш GitHub ~5 минут
2. копия того же файла на витрине — страховка, если GitHub недоступен; отстаёт до часа

У каждого запроса есть таймаут 5 секунд. Недоступная сеть далеко не всегда отвечает
отказом: если пакеты молча теряются, запрос висит до TCP-таймаута, и всё это время
страница пустая, хотя копия лежит на том же домене. Запросы к API на запись
ограничены двадцатью секундами по той же причине — иначе кнопка «Публикую…»
висела бы бесконечно.

Поэтому опубликованные правки видны через несколько минут, а не через час:
часовая синхронизация подрядчика тащит только саму страницу, но не данные.

Если не ответил ни один источник, страница честно пишет, что расписание не
загрузилось. Третьим рубежом раньше служило расписание, вшитое прямо в `index.html`,
но его убрали: оно было заморожено на сентябре–декабре 2026 и в этом редком случае
выдавало прошлый поток за настоящий, ничем это не обозначая. Заодно оно маскировало
пустое опубликованное расписание — страница показывала вшитое вместо пустоты.

Страница различает три исхода и говорит о них по-разному: расписание загружено;
источник ответил, но расписание пустое (нормально для потока или черновика,
который ещё не собрали);
источник не ответил вовсе — это сбой.

Кнопка «Опубликовать» коммитит JSON в этот репозиторий через Contents API.
Если запрос не прошёл, страница честно объясняет причину и скачивает `data.json`,
чтобы его можно было залить в репозиторий руками.

Время во всех сообщениях коммитов — **московское** (UTC+3). Раньше писалось UTC,
из-за чего у публикующих из других поясов день около полуночи получался вчерашним.

## Отмена правок и откат публикаций

**Вернуть опубликованное** — отменяет правки на странице и возвращает расписание,
которое прямо сейчас видят студенты. В репозиторий ничего не пишет. Если не ответили
ни GitHub, ни витрина, кнопка ничего не подставляет и не трогает правки редактора —
он просил опубликованное, а не что-то взамен, — и сообщает, что произошло.

**История** — список последних 20 публикаций файла того расписания, на странице которого
вы находитесь, с датой, автором и сообщением коммита. Заливки из черновика помечены
отдельно, текущая версия — как «сейчас на сайте».
Выбранная версия загружается в страницу для просмотра; на сайте ничего не меняется,
пока не нажать «Опубликовать». Состав версии (сколько месяцев и занятий) показывается
после загрузки, а не в списке: иначе пришлось бы скачивать все 20 версий разом.

Важно понимать, что **каждый клик по «Опубликовать» — отдельный коммит**, поэтому
«предыдущая версия» обычно означает то же расписание без одной исправленной опечатки,
а не прошлый релиз. Из-за этого история сделана списком с датами, а не кнопкой
«шаг назад»: нужную точку выбирает человек.

Если, пока вы выбирали версию, кто-то успел опубликовать свою правку, публикация
отменится с объяснением — чтобы старая версия не затёрла чужую работу. История
читается и без токена (репозиторий публичный), так что остаётся рабочей, даже
если токен истёк.

## Черновик и заливка в расписание

Черновик — место, где расписание собирают до того, как отдать его студентам.
Адрес с `?test`, например `…/raspisanie-shkoly-crm/?test#edit`. Сверху жёлтая плашка,
данные в отдельном файле `data-test.json`, свой ключ хранения в браузере. Ни одно
расписание при работе с черновиком не затрагивается.

Ссылку с `?test` студентам не дают — но это договорённость, а не защита: репозиторий
публичный, и `data-test.json` читается кем угодно, кто знает адрес.

**Пока `data-test.json` не создан, черновик открывается полностью пустым** — без месяцев
и занятий, с подсказкой на месте расписания. Так и задумано: у нового потока свои
месяцы, и начинать удобнее с чистого листа, а не вычищать прошлый.

В черновике в панели редактирования появляются две кнопки, и обе показывают **список
существующих расписаний** с их названиями и адресами:

```
1 — Осенний поток 2026 (основной адрес)
2 — без названия (?stream=2)
```

- **Взять из расписания…** — заполнить черновик выбранным расписанием, если нужно
  править от готового. В репозиторий ничего не пишет, только в страницу
- **Залить в расписание…** — перенести то, что на странице, в файл выбранного
  расписания. Подтверждение называет цель в том же виде, что список, и показывает
  состав: сколько месяцев и занятий, какие месяцы

Редактор выбирает **строку списка**, а не номер потока. Список собирается запросом
каталога `assets/` к GitHub и чтением названий с CDN, так что лимит запросов к API
не тратится, а черновик в цели заливки не попадает. Если список получить не удалось —
нет связи, лимит без токена, истёкший токен, — кнопка не отключается: она честно
говорит об этом и спрашивает адрес напрямую.

Один и тот же черновик можно залить в любое расписание — они независимы.
Заливка заменяет расписание потока целиком, а не дополняет его; прошлая версия
остаётся в истории и достаётся кнопкой «История» на странице этого потока.

Пустой черновик залить нельзя — кнопка откажется, чтобы случайный клик в свежем
черновике не обнулил живое расписание. «Сбросить» в черновике называется «Очистить»
и стирает всё до пустого листа.

Отдельная копия репозитория и второй токен для этого не нужны: страница одна на все
потоки и на черновик, поэтому они не могут разъехаться по вёрстке.

## Аватарки

Требования к файлам и карта «кто есть кто» — в `assets/avatars/README.txt`.

Фото можно загрузить **прямо из редактора**: в панели дня есть поле «Фото спикера».
Файл любых пропорций приводится к PNG 120×120 (кадрируется как в вёрстке —
по центру по горизонтали и от верха) и коммитится в `assets/avatars/`.
Имя файла берётся из поля «файл», а если оно пустое — транслитерируется
из фамилии: «Трофим Рудзий» → `rudziy`.

Фото уходит в репозиторий сразу при выборе файла, отдельно публиковать не нужно.
Картинка ищется сначала на витрине, при промахе — напрямую в GitHub, поэтому
только что загруженное фото видно сразу. Если файла нет нигде, показываются инициалы.

HEIC с айфона браузер не открывает — редактор про это скажет и попросит JPG или PNG.

## Токен GitHub

Редактор пишет по fine-grained personal access token с правом
`Contents: Read and write` только на этот репозиторий.

**Токен истекает 15 января 2027.** После этой даты публикация молча перестанет
работать — кнопка будет сообщать, что токен недействителен. Перевыпустить:
https://github.com/settings/tokens?type=beta (fine-grained, only this repository,
Contents: Read and write), затем заменить части в `GH_TOKEN_PARTS` в `index.html`.

**Токен разбит на три части и склеивается в рантайме.** Это не защита: страница
публичная, собрать его обратно может любой, кто откроет исходники. Смысл в другом —
GitHub сам сканирует публичные репозитории на свои токены и автоматически отзывает
найденные, а Push Protection может заблокировать коммит. Если вписать токен одной
строкой, он умрёт в первые минуты. Первый разрез делайте внутри префикса
`github_pat_`, чтобы разбить и его.

Риск открытого токена принят осознанно: ценность данных низкая, права ограничены
одним репозиторием и только записью файлов, git даёт полную историю — любую
порчу видно и можно откатить через `git revert`. Пароль редактора в этой схеме —
удобство, а не защита: раз токен в коде, проверку пароля можно обойти.

Полезно включить уведомления на push (Settings → Notifications), чтобы узнать
о посторонней записи сразу.

## Пароль редактора

Строка `const EDIT_PASS='…'` в `index.html`. Меняется в одном месте, перезапускать
нечего — коммит и подождать синхронизацию.

## Витрина и домен

Доменом и витриной управляет подрядчик: он забирает содержимое `assets/`
из этого репозитория примерно раз в час и раскладывает по адресу выше.
Прямого доступа к его инфраструктуре нет, со стороны страницы настраивать нечего.

Из этого следуют две разные задержки, которые полезно не путать:

| Что изменили | Когда видно |
|---|---|
| Расписание (`data.json`) | несколько минут — читается напрямую из GitHub |
| Фото спикера | сразу — при промахе витрины берётся из GitHub |
| Саму страницу (`index.html`) | до часа — ждём синхронизации подрядчика |

## Что не решено

Репозиторий и токен живут на личном GitHub-аккаунте — если владелец уйдёт,
публикация останется без присмотра. Правильное решение — перенести репозиторий
в корпоративный аккаунт Mindbox, когда появится доступ, и перевыпустить токен
оттуда. Перенос сохраняет историю, но потребует поменять `GH_OWNER` в `index.html`
и попросить подрядчика сменить источник синхронизации.
